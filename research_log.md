### Отобранные БД (3 шт.):
1. **`toxicology`**(4 таблицы)
    - *Причина выбора:* для проверки гипотезы о графовых связях. Нестандартная предметная область (молекулы-атомы-связи) требует от модели нетривиального schema linking, что подходит для проверки правильности определения архитектуры Light-RAG.
2. **`financial`** (8 таблиц)
   - *Причина выбора:* бизнес-схема среднего размера, содержит множественные JOIN пути, что позволяет объективно оценить, насколько сокращение контекста через RAG влияет на точность сложных запросов.

3. **`codebase_community`** (8 таблиц)
   - *Причина выбора:* высокая степень связности (многие таблицы ссылаются на users и posts). Наличие сложных JOIN.

## 2. Лог экспериментов

### Эксперимент 1: Baseline (Week 1)


#### Этап А: Отладка и калибровка eval-harness (22 вопроса)
- **Дата:** [17.07.2026]
- **Модель:** Qwen2.5-Coder-7B-Instruct
- **Вопросы:** bird_small.json (22 вопроса)
- **Промпт:** Zero-shot, полная схема БД в контексте.
- **Выявленные проблемы:
1. Падение при исчерпании попыток. При MAX_RETRIES=7, если модель не могла сгенерировать валидный SQL, возникала ошибка UnboundLocalError: cannot access local variable 'final_result'. Исправлено: добавлена инициализация final_result = {"status": "error", "query": "error"} до начала цикла, что позволяет eval-harness корректно засчитать такой запрос как score = 0, а не прерывать весь прогон.
2. Валидация sqlglot: Зафиксировано, что модель часто генерирует синтаксически невалидный для PostgreSQL код (ошибки алиасов, незакрытые скобки), который отлавливается нашим санитайзером. Это ожидаемое поведение для zero-shot 7B модели.

- **Предварительные метрики:** EX ≈ 22.73%, средний расход ~2 500 prompt-токенов на запрос. Выборка признана нерепрезентативной для финальных выводов.

#### Изменения в коде 

**Этап Б: Внедрение R-VES и стабилизация eval-harness (27.07.2026)**

1. **Реализация официальной метрики R-VES (Reward-based Valid Efficiency Score)**
   - *Изменения в `benchmarks/evaluate_bird.py`:*
     - Добавлена функция `clean_abnormal()` (правило 3-х сигм) для отсечения выбросов времени выполнения.
     - Внедрен многократный прогон (`iterate_num=5`) для корректных запросов с расчётом дискретной награды (0.25 – 1.25) на основе соотношения времени `gold_time / pred_time`.
     - Добавлена защита от деления на ноль: `safe_t_pred = max(t_pred, 0.0001)`.
   - *Количественный эффект:* Метрика эффективности стала устойчивой к случайным скачкам времени отклика PostgreSQL (кэш ОС/диска), обеспечивая честное сравнение с лидербордом BIRD.

2. **Защита инфраструктуры от зависаний**
   - *Изменения:* Добавлен `SET statement_timeout = 3000` перед каждым исполнением SQL в `evaluate_bird.py`.
   - *Количественный эффект:* Предотвращено зависание скрипта >30 минут на сгенерированных декартовых произведениях; такие запросы теперь честно получают `score=0, ves_reward=0.0`.

3. **Артефакты для DoD: сохранение результатов**
   - *Изменения:*
     - Вынесена функция `save_manual_check()` в `evaluate_bird.py` для генерации `manual_check.json` (ручная верификация).
     - Обновлён `bird_benchmark.py` для сохранения `baseline.csv` с колонками: `db_id`, `EX_percent`, `VES_percent`, `prompt_tokens_per_query`, `total_queries`.
   - *Количественный эффект:* Обеспечена воспроизводимость метрик одной командой, выполнена ручная сверка 10 примеров (требование DoD Недели 1).
