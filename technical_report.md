# Технический отчёт AdvText2SQL: baseline и LightRAG для специализированного Text-to-SQL

- **Проект:** DB2Model / AdvText2SQL
- **Дата:** 24 августа 2026 г.
- **Основной benchmark:** BIRD, 91 вопрос по трём PostgreSQL-базам
- **Target-модель:** `Qwen/Qwen2.5-Coder-7B-Instruct`

## Краткое резюме

В работе исследуется способ построения Text-to-SQL-системы, специализированной
под конкретную PostgreSQL-базу данных. Baseline передаёт target-модели полную
схему БД при каждом запросе. Экспериментальная ветка LightRAG сначала извлекает
из графа знаний только релевантный подграф, а затем формирует из него контекст
для генерации SQL.

Гипотеза подтвердилась частично. Семантически богатый контекст LightRAG V3
повысил Execution Accuracy с **23,08% до 28,57%** и VES с **18,96% до
25,27%**, но увеличил полный prompt budget на **53,35%**. Compact-вариант
уменьшил schema-only контекст на **70,6%**, однако его EX снизился до **19,78%**,
а с учётом стоимости retrieval полный prompt остался на **9,66%** дороже
baseline. На отдельном confirmation-наборе из двух самых широких схем Compact
уже сократил end-to-end prompt на **36,39%**, но сохранить качество SQL не
смог.

Главный вывод состоит в том, что retrieval нельзя оценивать только по размеру
извлечённой схемы. Необходимо одновременно учитывать полноту schema linking,
стоимость retrieval и размер исходной БД. Полученные результаты подталкивают к использованию
адаптивной стратегии: полная схема для небольших БД и структурный retrieval с
PK/FK-путями и релевантными значениями для широких схем.

## 1. Постановка задачи и гипотеза

Text-to-SQL-система преобразует вопрос пользователя на естественном языке в
SQL-запрос к реляционной базе данных. Для корректной генерации модели требуется
знание схемы: имён таблиц и колонок, типов данных, связей между таблицами и
семантики значений. На практике это знание часто передаётся в prompt при каждом
запросе. Такой подход прост, но его стоимость растёт вместе с шириной схемы, а
длинный контекст не гарантирует правильного schema linking.

Цель проекта - исследовать, можно ли автоматически собрать знания о конкретной
PostgreSQL-базе и передавать target-модели только ту их часть, которая нужна для
текущего вопроса. Работа разделена на две подзадачи:

1. **Exploration:** извлечь из PostgreSQL структурированное и семантическое
   описание БД.
2. **Distillation без обучения:** представить знания в виде графа и извлекать
   query-specific подграф через LightRAG.

Основная гипотеза формулировалась следующим образом:

> Релевантный подграф LightRAG позволит уменьшить объём schema context без
> снижения качества SQL относительно zero-shot baseline с полной схемой.

Гипотеза проверялась по трём группам метрик:

- **EX (Execution Accuracy):** доля запросов, результат выполнения которых
  совпал с результатом gold SQL;
- **VES:** эффективность корректных запросов с учётом отношения времени
  выполнения predicted и gold SQL;
- **token budget:** размер schema-only контекста, prompt target-модели,
  дополнительный retrieval prompt и их end-to-end сумма.

Сравнение проводилось на одном split, с одной target-моделью, одинаковым BIRD
evidence и общей логикой выполнения и оценки SQL. Неуспешные, ошибочные и
`ambiguous` ответы не исключались из знаменателя и получали нулевой score.

реалистичных Text-to-SQL-задач с привязкой к содержимому реляционных БД. Для
основного эксперимента из BIRD dev заранее были выбраны три базы с разными
размерами и структурой. Выбор сделан до финального сравнения EX/VES и основан
на топологии схем и ожидаемой полезности для проверки retrieval.

| База данных | Вопросов | Таблиц | Колонок | FK | Полная схема, cl100k | Роль в эксперименте |
| :--- | ---: | ---: | ---: | ---: | ---: | :--- |
| `toxicology` | 35 | 4 | 11 | 3 | 88 | Маленькая графоподобная схема; контроль стоимости retrieval |
| `financial` | 29 | 8 | 55 | 8 | 418 | Бизнес-схема с несколькими multi-hop JOIN-путями |
| `codebase_community` | 27 | 8 | 71 | 7 | 568 | Связная схема и stress-test для schema linking |
| **Итого** | **91** | — | — | — | **335,58, взвешенно** | Основной зафиксированный split |

Файл [`data/bird_large_filtered.json`](data/bird_large_filtered.json) содержит
91 уникальный вопрос: 35 для `toxicology`, 29 для `financial` и 27 для
`codebase_community`. Для каждого примера сохранены `question_id`, `db_id`,
естественно-языковой вопрос, BIRD evidence, сложность и gold SQL. Обучающие
данные не использовались при retrieval или генерации на evaluation split.

Дополнительно была проверена гипотеза о влиянии ширины схемы БД на количество токенов. Сначала восемь доступных BIRD-схем
были независимо профилированы по точному размеру baseline-сериализации. Затем
для confirmation-прогона выбраны две самые широкие схемы: `card_games`
(891 schema token) и `california_schools` (762 token), всего 55 вопросов. Этот
набор не входил в исходные три базы, но проверял только гипотезу о влиянии
ширины схемы.

## 3. Exploration-pipeline

Exploration-pipeline преобразует PostgreSQL в набор воспроизводимых артефактов,
которые далее используются baseline, LightRAG и MCP-прототипом:

```text
PostgreSQL
  - structured knowledge JSON
  - M-Schema и semantic descriptions
  - NetworkX knowledge graph
  - LightRAG storage
  - query-specific retrieval
  - schema context для target-модели
```

### 3.1. Извлечение структурированных знаний

Скрипт [`scripts/explore_database.py`](scripts/explore_database.py) читает
PostgreSQL через read-only соединение и извлекает:

- таблицы, колонки и SQL-типы;
- первичные и внешние ключи;
- комментарии к таблицам;
- статистики `pg_stats`, включая `n_distinct`, `most_common_vals`,
  `null_frac` и гистограммы;
- до пяти примеров строк для каждой таблицы.

Результат сохраняется в
`artifacts/db_knowledge/<db>_knowledge.json`. На этом шаге LLM не вызывается.

### 3.2. M-Schema и семантическое описание

[`scripts/generate_m_schema.py`](scripts/generate_m_schema.py) создаёт два
представления БД:

- `<db>_m_schema.txt` - детерминированная полуструктурированная сериализация;
- `<db>_semantic.txt` - описания таблиц и колонок, сгенерированные
  Teacher-LLM поверх извлечённых метаданных.

Таким образом, сырые имена и типы дополняются человекочитаемой семантикой, но
исходный structured knowledge остаётся отдельным артефактом и источником
структурных фактов.

### 3.3. Граф знаний

[`scripts/build_db_graph.py`](scripts/build_db_graph.py) строит NetworkX-граф.
В нём представлены узлы таблиц, колонок и отобранных справочных значений, а
структурные рёбра описывают принадлежность колонки таблице, внешние ключи и
связь значения с колонкой. Диагностические эксперименты показали, что
`SEMANTICALLY_RELATED`-рёбра по похожести имён добавляли шум, поэтому в
финальный LightRAG storage они не загружались.

Граф сохраняется в форматах Pickle и GraphML вместе со статистикой. GraphML
используется для визуальной инспекции, а Pickle - как вход следующего шага и как удобных формат для отдельной реализации графового RAG.

### 3.4. Загрузка и retrieval LightRAG

[`scripts/load_to_lightrag.py`](scripts/load_to_lightrag.py) преобразует граф в
LightRAG custom knowledge graph и создаёт постоянное storage. Embedding-модель
`BAAI/bge-m3` кодирует сущности и отношения. На запросе используется hybrid
retrieval по entities, relationships и table chunks.

Финальная конфигурация основного benchmark:

- `lightrag-hku==1.5.4`;
- hybrid mode;
- `top_k = 15`, `chunk_top_k = 8`;
- reranking отключён;
- `BAAI/bge-m3`, 1024 измерения, CPU;
- `Qwen/Qwen2.5-Coder-7B-Instruct` для keyword extraction;
- холодная локальная копия storage без переиспользования keyword cache;
- BIRD evidence включён.

После retrieval выполняется постобработка: фильтрация нерелевантных VALUE-узлов,
выделение core-таблиц и восстановление необходимых FK-путей. Контекст для
target-модели собирается из итогового подграфа, а не только из исходных chunks.

Полные команды запуска и карта артефактов приведены в
[`README.md`](README.md) и [`scripts/README.md`](scripts/README.md).

## 4. Baseline и LightRAG

### 4.1. Baseline

Baseline использует `Qwen/Qwen2.5-Coder-7B-Instruct` при `temperature = 0` и
не выполняет retrieval. В каждый запрос передаётся полная lightweight-схема
соответствующей БД в формате:

```text
TABLE <table_name>
  <column_name> (<SQL_TYPE>)
```

В prompt также включается BIRD evidence. Сначала отдельный ambiguity-check
решает, достаточно ли данных для ответа, после чего target-модель генерирует
SQL. Сгенерированный запрос проходит нормализацию и исполняется в PostgreSQL с
`statement_timeout = 3000` мс. Его результат сравнивается с результатом gold
SQL.

Для корректных запросов VES использует пять повторов времени исполнения,
отсечение аномальных значений по правилу трёх сигм и дискретную награду на
основе отношения `gold_time / predicted_time`. Ручная стратифицированная
проверка десяти примеров не выявила расхождений между сохранёнными исходами и
автоматической оценкой.

### 4.2. Эволюция LightRAG

Разработка retrieval проходила через несколько диагностических этапов:

1. **V1: embedding + BFS.** Семантический поиск seed-узлов и BFS радиуса 1
   работали на простом запросе, но теряли multi-hop JOIN-пути и могли возвращать
   почти пустой контекст.
2. **V2: библиотечный LightRAG.** Hybrid retrieval повысил recall, а
   постобработка начала восстанавливать кратчайшие FK-пути. Одновременно
   выявился новый источник шума: ошибочно выбранная core-таблица расширяла
   подграф по реальным, но нерелевантным FK.
3. **V2.1–V2.2.** Были добавлены фильтрация VALUE-узлов и выбор core-таблиц,
   затем из LightRAG storage исключены `SEMANTICALLY_RELATED`-рёбра. После
   ручной проверки настройка под отдельные вопросы была остановлена, чтобы не
   подгонять retrieval под evaluation split.
4. **Semantic V3.** На полном split target-модель получала найденные сущности,
   структурные связи, релевантные значения и развёрнутые семантические
   описания. Это quality-first вариант.
5. **Compact V4.** Тот же тип retrieval сериализовался только как найденные
   таблицы, колонки и SQL-типы. Это economy-вариант без длинной семантики,
   PK/FK-описаний и VALUE-узлов в target context.

V3 и Compact исследуют разные рабочие режимы, но не являются строгой
serializer-only абляцией: при холодном LLM retrieval наборы таблиц совпали в
74 из 91 случая, а наборы колонок — только в 42 из 91. Поэтому разницу качества
нельзя полностью приписать формату сериализации.

### 4.3. Подсчёт token budget

В отчёте различаются три стоимости:

- **schema-only** - длина сформированной строки схемы в `cl100k_base`; это
  proxy размера представления, а не provider usage;
- **target prompt** - фактические prompt-токены всех вызовов target-пайплайна;
- **retrieval prompt** - дополнительные токены LLM-based keyword extraction;
- **end-to-end prompt** - сумма target и retrieval prompt.

Сравнивать только schema-only недостаточно: маленькая найденная схема может
сопровождаться дорогим retrieval-вызовом. С другой стороны, end-to-end budget
зависит от поведения pipeline: ранний `ambiguous` уменьшает число последующих
SQL-generation вызовов. Поэтому schema-only и end-to-end показатели
интерпретируются совместно.

## 5. Финальная таблица результатов

Ниже приведено основное сравнение на 91 вопросе. Для baseline используется
контрольный rerun от 16 августа с исправленным per-database подсчётом токенов.
Все варианты используют один split, BIRD evidence и target-модель семейства
Qwen2.5-Coder-7B.

| Подход | Контекст БД | Верных | EX, % | VES, % | Schema-only, cl100k/вопрос | Target prompt/вопрос | Retrieval prompt/вопрос | End-to-end prompt/вопрос |
| :--- | :--- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| **Baseline** | Полная `table + column + type` | 21/91 | **23,08** | **18,96** | 335,58 | 2 196,33 | 0 | **2 196,33** |
| **LightRAG Semantic V3** | Найденный подграф + связи + values + semantic descriptions | **26/91** | **28,57** | **25,27** | 629,26 | 2 663,52 | 704,54 | 3 368,05 |
| **LightRAG Compact** | Найденные `table + column + type` | 18/91 | 19,78 | 17,58 | **98,52** | **1 703,90** | 704,54 | 2 408,44 |

Относительно контрольного baseline:

- Semantic V3 дал **+5,49 п.п. EX** и **+6,32 п.п. VES**, но увеличил
  end-to-end prompt на **53,35%**;
- Compact уменьшил schema-only контекст на **70,6%** и target prompt на
  **22,42%**, но после учёта retrieval оказался на **9,66%** дороже baseline;
- Compact потерял **3,30 п.п. EX** и около **1,37 п.п. VES**.

Детализация качества по БД:

| БД | Baseline EX / VES | Semantic V3 EX / VES | Compact EX / VES |
| :--- | ---: | ---: | ---: |
| `toxicology` | 31,43 / 25,00 | **34,29 / 31,43** | 17,14 / 16,43 |
| `financial` | 13,79 / 11,21 | **24,14 / 22,41** | 17,24 / 14,66 |
| `codebase_community` | 22,22 / 19,44 | 25,93 / 20,37 | **25,93 / 22,22** |
| **Overall** | 23,08 / 18,96 | **28,57 / 25,27** | 19,78 / 17,58 |

Semantic V3 показал лучшее наблюдаемое качество на основном split. Compact
оказался полезнее на двух более крупных исходных схемах, но резко проиграл на
`toxicology`, где полная схема занимает всего 88 token и retrieval overhead не
окупается.

### Confirmation на широких схемах

На `card_games` и `california_schools` полная схема в среднем занимала 834,71
schema token. На этих 55 вопросах Compact показал ожидаемую экономию:

| Метрика | Baseline | Compact | Изменение |
| :--- | ---: | ---: | ---: |
| Schema-only, cl100k/вопрос | 834,71 | 107,58 | **−87,11%** |
| End-to-end prompt/вопрос | 3 336,93 | 2 122,51 | **−36,39%** |
| EX | 5,45% | 3,64% | −1,82 п.п. |
| VES | 4,09% | 2,73% | −1,36 п.п. |
| `ambiguous` | 2/55 | 24/55 | +22 ложных отказа |

Scale-гипотеза об экономии prompt подтвердилась, но гипотеза о сохранении
качества - нет.

## 6. Анализ ошибок и ограничения

### 6.1. Ошибка ambiguity-prompt

Первый baseline выявил системную проблему до этапа SQL generation. Изначальный
ambiguity-prompt требовал полностью заданных периода, агрегации и метрики и
помечал как неоднозначные вопросы, допускающие стандартную SQL-интерпретацию.

Prompt был изменён так, чтобы:

- отсутствие периода означало использование всех доступных данных;
- `best`, `worst` и `top` интерпретировались через `ORDER BY` и `LIMIT`;
- агрегация выбиралась по смыслу вопроса;
- отказ происходил только при отсутствии требуемых данных в схеме или
  бессмысленности вопроса.

В исторической baseline-итерации число ложных `ambiguous` снизилось с 21 до 11
(с 23,08% до 12,09%), EX вырос с 21,98% до 24,18%, а EX на `financial` — с
10,34% до 20,69%. Этот эксперимент показывает, что качество Text-to-SQL зависит
не только от генератора: слишком строгий safety-gate может искусственно
занижать метрики всей системы.

Значение 24,18% относится к историческому прогону после изменения prompt. В
финальной таблице используется более поздний контрольный baseline-rerun
23,08%, выполненный для сопоставимого подсчёта токенов. Разницу между двумя
прогонами нельзя приписать одному фактору из-за недетерминированности backend и
неполной self-contained конфигурации старого артефакта.

### 6.2. Ошибки retrieval

Основной недостаток Compact - недостаточная полнота schema linking:

- пропуск необходимой таблицы или колонки;
- отсутствие JOIN key даже при найденных бизнес-колонках;
- потеря точного literal value или колонки, на которую указывает evidence;
- пустой или слишком маленький набор seed-узлов;
- выбор лишней core-таблицы и последующее разрастание по реальным, но
  нерелевантным FK;
- несколько структурно допустимых, но семантически неверных JOIN-путей.

На confirmation-наборе для `card_games` два baseline-only успеха согласуются с
неполным retrieval: в одном случае отсутствовала `cards.artist`, в другом —
`cards.uuid`, `legalities.uuid` и `legalities.status`. Рост ложных `ambiguous`
до 24 из 55 дополнительно показывает, что неполный контекст часто блокировал
генерацию ещё до SQL.

### 6.3. Ошибки target-модели

Даже при достаточном контексте target-модель могла:

- использовать несуществующие колонки;
- создавать неправильные alias;
- выбирать неверную агрегацию или условие;
- генерировать несколько SQL-операторов вместо одного;
- строить исполнимый, но семантически неверный JOIN.

Следовательно, высокий recall retrieval необходим, но сам по себе не
гарантирует корректный SQL.

### 6.4. Ограничения эксперимента

1. **Один основной запуск.** Прирост V3 равен пяти дополнительным правильным
   ответам относительно контрольного rerun. Без нескольких повторов нельзя
   утверждать статистически устойчивое превосходство.
2. **Нестабильность baseline.** Исторический и контрольный baseline дали
   24,18% и 23,08% EX. Старый артефакт не содержит полного `run_config.json`,
   поэтому влияние backend drift и окружения нельзя разделить.
3. **V3 против Compact - не строгая абляция.**  LLM retrieval был
   недетерминированным; совпадение таблиц составило 74/91, колонок — 42/91.
4. **Известная ошибка evaluator.** Legacy-нормализация может портить отдельные
   gold SQL с делением, `NULLIF` или `/` внутри quoted identifiers. Относительное
   сравнение основного split частично сохраняется, но абсолютные EX/VES могут
   быть занижены. Вопрос №309 также содержит расхождение текста и gold SQL.
5. **Шум VES.** Время измерялось на удалённой PostgreSQL и зависит от
   состояния кэша и нагрузки. Небольшие различия VES не следует трактовать
   как доказанный эффект.
6. **Ограниченный масштаб.** Основной split содержит только 91 вопрос и три
   БД. Confirmation использует две широкие, но слабосвязные схемы и проверяет
   прежде всего влияние числа колонок, а не сложность FK-графа.
7. **MCP не был отдельным benchmark-режимом.** MCP использует собственный
   prompt и маршрутизацию, поэтому метрики baseline или LightRAG нельзя
   автоматически приписывать MCP-прототипу.

## 7. Вывод и дальнейшая работа

Исходная гипотеза подтвердилась частично:

- LightRAG способен повысить качество, если возвращает не только имена
  объектов, но и семантику, структурные связи и значения;
- богатый Semantic V3-контекст оказался дороже полной baseline-схемы;
- Compact существенно сжимает schema representation, но теряет критичные
  колонки, JOIN keys и literal values;
- end-to-end экономия появляется на действительно широких схемах, однако сама
  ширина схемы не гарантирует сохранения качества.

Практический результат проекта — воспроизводимый pipeline
`PostgreSQL → structured knowledge → M-Schema → graph → LightRAG → SQL`, общий
eval-harness и MCP-прототип. MCP генерирует read-only SQL, проверяет синтаксис и
при необходимости выполняет только `EXPLAIN`; фактическое исполнение SQL и
расчёт EX/VES остаются задачей доверенного клиента или benchmark harness.

Наиболее обоснованные направления дальнейшей работы:

1. **Проверить Structural-контекст:** найденные таблицы, колонки и типы плюс
   PK/FK-пути и релевантные literal values, но без длинных semantic
   descriptions. Это промежуточная точка между V3 и Compact.
2. **Сделать retrieval воспроизводимым:** сохранять сырой retrieval snapshot и
   повторно сериализовать один и тот же подграф разными форматами. Это позволит
   провести строгую serializer-only абляцию.
3. **Запускать несколько повторов:** фиксировать prompt hashes, commit,
   dirty-state, endpoint и per-question stability, а затем сообщать среднее и
   разброс EX/VES.
4. **Исправить evaluator и повторить confirmation:** удалить повреждающую
   regex-нормализацию, вручную проверить затронутые gold SQL и только затем
   обновить абсолютные метрики широких схем.
5. **Обучить router на отдельном validation split:** использовать размер
   полной схемы, сложность вопроса, наличие FK и coverage retrieval, но не
   подбирать пороги на финальном evaluation split.
6. **Разделить две scale-гипотезы:** отдельно оценивать широкие схемы с большим
   числом колонок и структурно сложные схемы с длинными FK-путями.
7. **Проверить гибрид с SFT/LoRA:** использовать компактную
   специализированную модель как основной генератор, а Structural retrieval —
   как объяснимый fallback для новых или изменившихся объектов БД.

Таким образом, работа не выявила одного универсально лучшего представления
схемы, но установила измеримый quality–cost trade-off и локализовала причины,
по которым retrieval теряет качество. Это создаёт проверяемую основу для
адаптивного Text-to-SQL-сервера, а не только набор разрозненных prompt-эвристик.
